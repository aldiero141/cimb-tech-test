# Spec — THT-MON-US-003: Fixed-Window Rate Limiter

> Generated by `/to-spec` from the grilling session (see `grilling-plan.md` in
> this folder) plus codebase context.

---

## Problem Statement

The call-monitoring API (`/api/auth/login`, `/api/calls`) currently has no
protection against brute-force or abusive clients. A single client can issue
unbounded requests, risking credential stuffing on login and DB load on
`GET /api/calls` (which runs a JPA Specification over PostgreSQL). There is no
throttling, no `429` path, and no client feedback when limits are exceeded.

## Solution

Implement a **deep, in-memory fixed-window rate limiter** per-endpoint,
keyed on client IP:

1. **Deep module** `FixedWindowRateLimiter` — one-method interface
   `RateLimitResult tryAcquire(compositeKey, rule)`, hiding all window math,
   storage (`ConcurrentHashMap`), and sweep. Injects `java.time.Clock` for
   deterministic tests. Deletion test passes: removing it scatters counting,
   reset, expiry, header logic across filter + two controllers.
2. **Seam** `RateLimitFilter extends OncePerRequestFilter` early in the
   Spring Security chain (before `JwtAuthFilter`). Matches `AntPathMatcher`
   against YAML rules; on deny writes `429 + Retry-After + JSON` and
   short-circuits. Exempts `actuator/health|info`.
3. **Config** `app.rate-limit` in `application.yml` — `enabled`, `trust-xff`,
   and `rules[] {path, limit, window-seconds}`. Defaults: `POST /api/auth/login
   5/60s`, `GET /api/calls 60/60s`.
4. **IP resolution** `IpKeyResolver` — `X-Forwarded-For` first value if
   `trust-xff`, else `remoteAddr`. Composite key `ip|path`.
5. **Frontend** — Axios 429 branch shows PrimeVue Toast
   `"Too many requests. Try again in Xs."` (no auto-retry, no auth clear).
6. **Boundedness** — lazy window reset + `@Scheduled(fixedDelay=300s)` purge of
   stale windows; all inside the module.

## User Stories

1. **As an operator**, I want login brute-force capped at 5/min per IP so
   credential stuffing is throttled (429 after 5, Retry-After header).
2. **As an operator**, I want `GET /api/calls` capped at 60/min per IP so a
   single user cannot starve others or overload PostgreSQL.
3. **As a client**, I want a clear `429` with `Retry-After` (header + JSON)
   so I know when to retry, without being signed out.
4. **As a maintainer**, I want limits tunable in `application.yml` without
   code changes, and the limiter swappable to Redis later without caller edits.

## Implementation Decisions

- **Modules built/modified**
  - **Backend**
    - `ratelimit/RateLimitProperties.java` — `@ConfigurationProperties(prefix="app.rate-limit")`
    - `ratelimit/RateLimitRule.java` — record / POJO
    - `ratelimit/RateLimitResult.java` — `allowed`, `retryAfterSeconds`
    - `ratelimit/FixedWindowRateLimiter.java` — `ConcurrentHashMap`, `Clock`, `@Scheduled` sweep, `tryAcquire`
    - `ratelimit/IpKeyResolver.java` — XFF vs remoteAddr
    - `ratelimit/RateLimitFilter.java` — `OncePerRequestFilter`, Ant matching, 429 JSON
    - `security/SecurityConfig.java` — register filter before `JwtAuthFilter`, enable scheduling if needed
    - `CallMonitoringApplication.java` — add `@EnableScheduling` if not present
    - `resources/application.yml` — add `app.rate-limit.rules`
    - Tests: `FixedWindowRateLimiterTest` (Clock.fixed boundaries), `RateLimitFilterTest` (MockMvc, XFF, header + body asserts)
  - **Frontend**
    - `services/api.ts` — Axios response interceptor 429 branch → `useToast`
    - Tests: `services/__tests__/api.test.ts` — 429 toast, no logout

- **Interface discipline**
  - External seam: `FixedWindowRateLimiter.tryAcquire` — only surface tests cross it.
  - Internal seams (not in interface): `Window` struct, `purgeStale`, Ant matcher — tested through the same public method.

## Out of Scope

- Sliding-window / token-bucket / leaky-bucket algorithms (same Interface would allow later swap; ADR documents fixed-window burst flaw).
- Redis distributed adapter (hypothetical second adapter — not introduced until multi-instance need is real).
- `X-RateLimit-Limit/Remaining/Reset` headers on success responses (YAGNI).
- Per-user (JWT subject) keying; IP-only in v1.

---

## Testing Strategy

1. **Backend unit (JUnit, MockMvc, Clock.fixed)**
   - `FixedWindowRateLimiterTest`: allow under limit; deny over limit with correct retryAfter; window rolls; composite-key isolation; concurrent `compute` safety.
   - `RateLimitFilterTest`: 6× login with same XFF → 6th is 429 with `Retry-After` header + JSON `retryAfter`; different IP passes; `/api/calls` has independent counter; actuator bypass.
2. **Frontend unit (Vitest)**
   - 429 interceptor shows toast with retryAfter detail, does not call `authStore.logout`.
   - 401 path still works (regression).
3. **E2E (Playwright)**
   - Loop login 6× with same `X-Forwarded-For` → last is 429; then advance/ wait window → allowed again (or mock Clock via test config).

## Further Notes

- Pure fixed window burst is documented in README/ADR: `5@00:59 + 5@01:01 = 10/2s`.
- `trust-xff=true` assumes nginx sets `X-Forwarded-For`; in tests set header explicitly.
- Thread safety: use `ConcurrentHashMap.compute` (atomic per-key) — not `get` then `put`.
