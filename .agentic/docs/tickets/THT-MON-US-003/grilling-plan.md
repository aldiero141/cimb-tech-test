# Grilling Plan — THT-MON-US-003: Fixed-Window Rate Limiter

> Generated by a `/grilling` session (grill-with-docs + codebase-design) against
> `THT-MON-US-003` (Fixed-window rate limiter for the call-monitoring API).
>
> This document captures every decision from the interview, the ADRs, the
> glossary, and the concrete implementation plan. The synthesized spec lives
> alongside this file as `to-spec.md`. Codebase-design vocabulary (Module,
> Interface, Seam, Adapter, Depth, Leverage, Locality) is used throughout.

---

## 1. Summary

Protect the Spring Boot API from brute-force and abusive clients with a
**deep, in-memory fixed-window rate limiter**. The limiter is per-endpoint
selective, keyed on **client IP** (via `X-Forwarded-For`), implemented as a
`OncePerRequestFilter` early in the Spring Security chain, returning
`429 Too Many Requests` + `Retry-After` + JSON body. Window state is an
in-memory `ConcurrentHashMap` behind a one-method interface, with
`java.time.Clock` for testability and lazy expiry + periodic sweep for
boundedness. Frontend surfaces `429` via PrimeVue Toast (no auto-retry).

## 2. Interview Decisions (Q1–Q12)

| # | Question | Decision |
|---|----------|----------|
| Q1 | Scope / primary threat | **C — Per-endpoint selective** — different limits per path. Primary value is security + fairness, not single-endpoint brute-force. |
| Q2 | Limiter key | **Client IP only** — stateless, works for unauthenticated `/api/auth/login` and authenticated `/api/calls`. Composite key is `IP + matched rule path`. |
| Q3 | Window & limits (defaults) | **5 req / 60s for `POST /api/auth/login`** (brute-force), **60 req / 60s for `GET /api/calls`** (abuse/fairness). Values are YAML-configurable. |
| Q4 | Storage seam | **In-memory `ConcurrentHashMap`** — zero infra, sufficient for single-backend Docker deployment. Interface hides storage so a Redis adapter can replace it later without caller changes. |
| Q5 | Seam placement | **OncePerRequestFilter (RateLimitFilter)** — registered `addFilterBefore(JwtAuthFilter)` (i.e. before auth). Smallest interface, sees every `/api/**` request, cannot be bypassed by MVC mis-routing. Deletion test: removing filter scatters counting/reset/header logic across 2 controllers + SecurityConfig. |
| Q6 | 429 contract | **`429 Too Many Requests` + `Retry-After: <seconds>` + JSON** `{"status":429,"error":"Too Many Requests","message":"Rate limit exceeded. Try again in 28s.","retryAfter":28}`. Normal (non-limited) responses do NOT carry `X-RateLimit-*` yet (YAGNI; can add later behind same interface). |
| Q7 | Window semantics | **Pure fixed window** — `windowStart = floor(now / windowMs) * windowMs`. Document boundary-burst flaw (`5@00:59 + 5@01:01 = 10/2s`) in ADR. Same Interface would allow swapping to sliding window later without caller edits. |
| Q8 | Frontend behavior on 429 | **PrimeVue Toast** — `"Too many requests. Try again in Xs."` No auto-retry / no backoff interceptor. Axios 401 interceptor stays distinct; 429 is a separate branch. |
| Q9 | Config & bypass | Two rules in `application.yml` under `app.rate-limit.rules`; `actuator/health` and `actuator/info` are exempt (no limit). Config shape: `path` (Ant pattern), `limit`, `window-seconds`. |
| Q10 | IP extraction | **`X-Forwarded-For` first value**, trimmed, fallback `request.getRemoteAddr()`. Trust is acceptable behind `frontend/nginx` proxy that sets `X-Forwarded-For`. Document `app.rate-limit.trust-xff: true` flag. |
| Q11 | Testability seam | **Inject `java.time.Clock`** into the rate-limiter module. Production wires `Clock.systemUTC()`. Tests inject `Clock.fixed(...)` and advance time without `sleep`. The filter is tested via `MockMvc`; the module via direct unit tests past the same Interface. |
| Q12 | Map bound / cleanup | **Lazy expiry + scheduled sweep** — on each `isAllowed` check, expired windows are reset. A `@Scheduled(fixedDelay=300000)` purges entries whose `windowStart + windowMs < now`. No hard `maxSize` needed for this traffic level; sweep guarantees locality of cleanup inside the module. |

## 3. Architecture Decision Records

### ADR-001: Fixed-Window Semantics (Not Sliding / Token-Bucket)

**Status:** Accepted

**Context:** Requirement says "fixed windows". Alternatives: sliding-window, leaky-bucket, Bucket4j token-bucket. Fixed window is simplest to implement and reason about.

**Decision:** Window is aligned to epoch: `windowStart = (nowMs / windowMs) * windowMs`. Per-key counter resets to 1 when `nowMs >= windowStart + windowMs`. Acknowledge burst at boundary in docs.

**Consequences:** O(1) per request, single `long + int` per key. Burst flaw accepted; interface `RateLimiter.isAllowed(key, rule) -> Result` would hide a future sliding-window implementation.

### ADR-002: Seam — OncePerRequestFilter Before JwtAuthFilter

**Status:** Accepted

**Context:** Options: Filter vs Interceptor vs `@RateLimit` AOP vs Bucket4j. Interceptor misses non-MVC paths; AOP expands interface (annotation per method); Bucket4j adds dependency without per-IP configurability advantage.

**Decision:** `RateLimitFilter extends OncePerRequestFilter`, ordered before `JwtAuthFilter` in `SecurityConfig`. It matches `request.getRequestURI()` against `app.rate-limit.rules[*].path` (Ant matcher). Unmatched or `actuator/*` paths pass through untouched. On deny, filter writes 429 and **does not** call `filterChain.doFilter`.

**Consequences:** One Interface for all callers; leverage = every controller benefits. Locality = window calc, storage, header writing live in one module.

### ADR-003: Key = Client IP via X-Forwarded-For

**Status:** Accepted

**Context:** Key could be user/JWT subj, but `POST /api/auth/login` is unauthenticated — IP is the only identifier. Using IP uniformly keeps the module deep (one key type). NAT sharing is mitigated by per-endpoint limits, not per-IP global limit.

**Decision:** `IpKeyResolver.resolve(request)` → `XFF.split(",")[0].trim()` if `app.rate-limit.trust-xff=true` and header present, else `remoteAddr`. Composite map key = `ip + "|" + rule.path`.

**Consequences:** Simple, stateless. Behind nginx `proxy_set_header X-Forwarded-For $remote_addr` the IP is real client IP. In tests, set the header explicitly.

### ADR-004: Storage — In-Memory ConcurrentHashMap Behind an Interface (Clock Injected)

**Status:** Accepted

**Context:** Single `postgres:16` + single `backend:8080` in `compose.yml`. Redis would add infra for no distributed need. Raw map risks unbounded growth and untestable time.

**Decision:** Deep module `FixedWindowRateLimiter` with interface:
```java
RateLimitResult tryAcquire(String key, RateLimitRule rule)
// or: boolean isAllowed(String key, RateLimitRule rule) + getRetryAfter()
```
Implementation: `ConcurrentHashMap<String, Window>`, `Window { long windowStartMs; AtomicInteger count }` (or synchronized per-key). Constructor takes `Clock`. Caller (filter) supplies `rule.limit()` and `rule.windowMs()`.

**Consequences:** Depth: one method, all window math hidden. Two adapters justify seam: `InMemory` (now) and `Redis` (future). Tests use `Clock.fixed` to verify boundaries deterministically. Thread-safe via `ConcurrentHashMap.compute`.

### ADR-005: Per-Endpoint Config in application.yml

**Status:** Accepted

**Context:** Requirement is per-endpoint selective. Need declarative, operator-tunable limits without code change.

**Decision:**
```yaml
app:
  rate-limit:
    enabled: true
    trust-xff: true
    rules:
      - path: /api/auth/login
        limit: 5
        window-seconds: 60
      - path: /api/calls
        limit: 60
        window-seconds: 60
```
`@ConfigurationProperties(prefix="app.rate-limit")` binds to `RateLimitProperties(RateLimitRule[ path, limit, windowSeconds ])`. First matching rule wins. No rule → pass. Filter is disabled if `enabled=false`.

**Consequences:** Operator can tune without redeploy logic; tests override via `@TestPropertySource`.

### ADR-006: 429 Contract — Retry-After + JSON

**Status:** Accepted

**Context:** HTTP 429 is the standard. Clients need to know when to retry. RFC says `Retry-After` can be seconds or HTTP-date; seconds is simpler.

**Decision:** On deny: `response.setStatus(429)`, `response.setHeader("Retry-After", String.valueOf(retryAfterSeconds))`, `Content-Type: application/json`, body `{"status":429,"error":"Too Many Requests","message":"Rate limit exceeded. Try again in Xs.","retryAfter":X}` where `X = ceil((windowStart + windowMs - nowMs)/1000)`. No `X-RateLimit-*` on success in v1.

**Consequences:** Frontend can read `retryAfter` without parsing header; header also satisfies spec/cURL users.

### ADR-007: Frontend — Toast on 429, No Auto-Retry

**Status:** Accepted

**Context:** Axios already has request interceptor (Bearer) + 401 auto-signout. 429 should not trigger signout or retry storm.

**Decision:** In `frontend/src/services/api.ts`, add `response` interceptor branch for `status===429`: extract `retryAfter` from response JSON or header, call `useToast().add({severity:'warn', summary:'Too many requests', detail: message})`. Do **not** retry. Do **not** clear auth. Callers can optionally read the error.

**Consequences:** User-visible feedback within `Retry-After` window. No thundering herd from auto-retry.

### ADR-008: Bounded Map — Lazy Reset + 5-Minute Sweep

**Status:** Accepted

**Context:** Map grows with distinct IPs. No LRU needed at expected scale, but must not leak forever.

**Decision:** On each access, if window expired, reset `windowStart` and `count`. Independently, `@Scheduled(fixedDelay=300_000)` iterates and removes entries where `now - windowStart > windowMs * 2` (or 5 min). Enabled via `@EnableScheduling`.

**Consequences:** All lifecycle stays inside the module (locality). No caller must call `cleanup`.

## 4. Glossary

| Term | Definition |
|---|---|
| **Fixed Window** | Rate-limit algorithm where time is partitioned into aligned windows of `W` seconds; each key gets at most `N` requests per window; counter resets at window boundary. |
| **Window Start** | Inclusive start of the current window: `floor(now / W) * W`. |
| **RateLimitRule** | Tuple `(path Ant-pattern, limit N, windowSeconds W)` loaded from `app.rate-limit.rules`. |
| **Composite Key** | `clientIp + "|" + rule.path` — isolates counters per endpoint per client. |
| **Retry-After** | Seconds until the current window resets; returned as header + JSON field on 429. |
| **Module (codebase-design)** | Unit with Interface + Implementation at a Seam; here `FixedWindowRateLimiter`. |
| **Interface** | What callers must know: `RateLimitResult tryAcquire(String compositeKey, RateLimitRule rule)` + config shape. |
| **Seam** | Location where the Interface lives: the `OncePerRequestFilter` boundary + the `RateLimiter` class boundary. |
| **Adapter** | Concrete thing at the seam: `InMemory` map adapter (now), `Redis` adapter (future). |
| **Trust-XFF** | Flag controlling whether `X-Forwarded-For` header is honored for IP extraction (required behind nginx). |
| **Sweep** | Periodic scheduled task removing stale window entries to bound memory. |

## 5. Implementation Plan

Ordered phases; Conventional Commits; single branch `feature/tht-mon-us-003-rate-limiter` (or `feature/rate-limiter-fixed-window`).

### Phase 0 — Properties & config

**Commit:** `feat(config): add rate-limit properties to application.yml`

- Add `app.rate-limit.enabled/trust-xff/rules` block to `backend/src/main/resources/application.yml` with two default rules (login 5/60s, calls 60/60s).
- Update `.env` docs if needed.

### Phase 1 — Deep module: FixedWindowRateLimiter (backend)

**Commits:**
1. `feat(backend): add FixedWindowRateLimiter module with Clock injection`
   - New package `com.cimb.callmonitoring.ratelimit`:
     - `RateLimitRule` (record: `String path; int limit; Duration window`)
     - `RateLimitProperties` (`@ConfigurationProperties(prefix="app.rate-limit")`, list of rules + enabled/trustXff)
     - `RateLimitResult` (record: `boolean allowed; int retryAfterSeconds; int remaining`)
     - `FixedWindowRateLimiter` (`@Component`) — `ConcurrentHashMap<String, Window>`, method `RateLimitResult tryAcquire(String compositeKey, RateLimitRule rule)`, `Clock` constructor, `compute`-based thread safety.
     - `Window` (package-private: `long windowStartMs; int count`)
     - `@Scheduled` purge method; `@EnableScheduling` on application or config.
2. `test(backend): add unit tests for FixedWindowRateLimiter with Clock.fixed`
   - Cases: within limit allowed; exceed → 429 + retryAfter; window rolls over resets; composite keys isolated; thread-safe concurrent access; Clock.advance.

### Phase 2 — Filter + SecurityConfig + KeyResolver

**Commits:**
3. `feat(security): add RateLimitFilter and IpKeyResolver`
   - `IpKeyResolver` (utility, `String resolve(HttpServletRequest)`)
   - `RateLimitFilter extends OncePerRequestFilter` — matches Ant path, calls limiter, writes 429 + Retry-After + JSON on deny.
   - Register in `SecurityConfig` via `addFilterBefore(rateLimitFilter, JwtAuthFilter.class)` (or before `UsernamePasswordAuthenticationFilter` and ensure order `RateLimit → Jwt`).
   - `/actuator/health`, `/actuator/info` bypass unconditionally.
4. `test(backend): add MockMvc tests for RateLimitFilter 429 flow`
   - Mock IP via `X-Forwarded-For`; 5 allowed → 6th is 429 with correct header/body; different IP not affected; different endpoint has independent counter; `Retry-After` decreases as window advances (Clock.fixed).

### Phase 3 — Frontend toast on 429

**Commits:**
5. `feat(frontend): surface 429 as PrimeVue Toast with Retry-After`
   - In `frontend/src/services/api.ts` (Axios instance): add `response.use` branch for `status===429` → toast `warn` with `retryAfter` detail.
   - No auto-retry; ensure 401 branch remains first.
6. `test(frontend): add Vitest test for 429 interceptor toast branch`
   - Mock Axios response 429 + retryAfter header/body; assert `useToast` called, no logout side-effect.

### Phase 4 — E2E + docs + verification

**Commits:**
7. `test(e2e): add Playwright scenario for rate limiting`
   - Hit `POST /api/auth/login` 6 times with same XFF header → 6th is 429.
8. `docs: document rate-limit config and burst caveat in README`
   - Add "Rate Limiting" section under configuration: defaults, YAML shape, Retry-After contract, burst note.
