# Grilling Plan — THT-MON-US-001: Call Monitoring

> Generated by a `/grilling` session (grill-with-docs) against user story
> `THT-MON-US-001` (As a Supervisor I want to monitor customer call sentiment).
>
> This document captures every decision from the interview, the ADRs, the
> glossary, and the concrete implementation plan. The synthesized spec lives
> alongside this file as `to-spec.md`.

---

## 1. Summary

A JWT-protected Spring Boot API backed by PostgreSQL, with a Vue 3 + PrimeVue
frontend, exposing a single supervisor call-monitoring table with search,
period filter, sentiment filter, sorting, and pagination.

## 3. Architecture Decision Records

### ADR-001: JWT Authentication for API Protection

**Status:** Accepted

**Context:** AGENTS.md hard-requires JWT protection on all `/api/**` endpoints
(except `/api/auth/**`). The user story does not mention auth, but this is a
project-wide constraint.

**Decision:** Implement full JWT auth as part of US-01:
- `User` entity with BCrypt-encoded passwords.
- `POST /api/auth/login` returns a signed JWT (JJWT 0.12.5).
- Spring Security filter chain validates the JWT on all `/api/**` except
  `/api/auth/**`.
- Frontend: Pinia auth store, Axios interceptor attaching
  `Authorization: Bearer <token>`, Vue Router guard redirecting
  unauthenticated users to `/login`.
- Default seeded user: `admin` / `admin123`.

**Consequences:** Auth is built once and reused by future stories. A login page
is included in US-01's definition of done.

---

### ADR-002: Server-Side Pagination via Spring Data `Page<T>`

**Status:** Accepted

**Context:** The table shows 5 records per page with Previous/Next controls.
Total dataset is 100 records.

**Decision:** Use Spring Data's `Page<T>` response shape:

```json
{
  "content": [...],
  "page": 0,
  "size": 5,
  "totalElements": 100,
  "totalPages": 20
}
```

- Default page size: 5.
- Page index: 0-based.
- Frontend uses PrimeVue DataTable's built-in paginator in server-side mode.

**Consequences:** No custom response wrapper needed. PrimeVue's paginator emits
page-change events; the composable calls the API with an updated `page` param.

---

### ADR-003: PrimeVue DatePicker Range Mode for Period Filter

**Status:** Accepted

**Context:** The user wants Start Period + End Period filter; preferred approach
is a single range DatePicker.

**Decision:** Use
`<DatePicker selectionMode="range" :minDate="threeMonthsAgo" :maxDate="today" />`.
The component binds to a `[Date, Date]` array. If range mode has issues during
implementation, fall back to two separate DatePicker components.

**Consequences:** Simpler UI (one picker instead of two). `minDate`/`maxDate`
clamp the selectable range to the latest 3 months client-side. The backend also
validates the dates.

---

### ADR-004: Server-Side Filtering, Sorting, and Search

**Status:** Accepted

**Context:** Three filters (search, period, sentiment) plus sorting and
pagination must compose in a single API request.

**Decision:** Single endpoint `GET /api/calls` with query parameters:

| Param | Type | Description |
|---|---|---|
| `q` | String | Full-text search across all columns (ILIKE) |
| `startDate` | ISO date | Inclusive lower bound for callTimestamp |
| `endDate` | ISO date | Inclusive upper bound for callTimestamp |
| `sentiment` | Enum | `below70` or `above70` |
| `sort` | String | Field: `callId`, `callTimestamp`, `csName`, `customerName`, `sentimentScore` |
| `order` | String | `asc` or `desc` (default `desc`) |
| `page` | Int | 0-based page index (default 0) |
| `size` | Int | Page size (default 5) |

Backend uses `JpaSpecificationExecutor<CallRecord>` with a
`Specification<CallRecord>` that ANDs all predicates. Any filter change resets
the page to 0 (frontend responsibility).

**Consequences:** One request, one response. The frontend composable manages all
filter state and triggers a refetch on any change.

---

### ADR-005: UUID for call_id, Long for Primary Key

**Status:** Accepted

**Context:** Need a user-facing call identifier plus a JPA primary key.

**Decision:**
- `id`: `Long`, `@GeneratedValue(strategy = IDENTITY)` — the JPA primary key.
- `callId`: `UUID`, unique, not null, generated server-side — the user-facing
  identifier displayed in the UI.

**Consequences:** `id` is internal; `callId` is the user-facing identifier. UUID
avoids sequential identifier leakage.

---

### ADR-006: Seed Data — 100 Records, 6 Months, Random Indonesian Names

**Status:** Accepted

**Context:** No data in PostgreSQL. The frontend cannot be developed without seed
data.

**Decision:** A `CommandLineRunner` seed component inserts 100 `CallRecord` rows
when the table is empty:
- **Date range:** random timestamps within the last 6 months.
- **CS names:** random from a pool (~20 common Indonesian names).
- **Customer names:** random from a separate pool (~30).
- **Sentiment scores:** weighted random — ~60% below 70, ~40% at or above 70.
- **callId:** random UUIDs.

**Consequences:** Enough data for 20 pages of 5. Weighted distribution makes the
sentiment filter meaningful.

---

### ADR-007: English UI

**Status:** Accepted

**Context:** The story mixes English and Indonesian column names.

**Decision:** All UI text is English. Column headers:

`No. | Call ID | Call Timestamp | CS Name | Customer Name | Sentiment Score`

Filter labels, empty state, and pagination labels are English.

**Consequences:** Consistent UX; Indonesian names appear only in data, not in UI
chrome.

## 4. Glossary

| Term | Definition |
|---|---|
| **Call Record** | A single customer call monitoring entry stored in PostgreSQL, containing call metadata and a sentiment score. |
| **Call ID** | UUID displayed to the user as the unique identifier for a call record. |
| **CS Name** | Customer Service agent name — the person who handled the call. |
| **Customer Name (Nama Nasabah)** | The customer who made the call. |
| **Sentiment Score** | Integer 0–100 representing customer sentiment. Below 70 = negative; 70+ = positive. |
| **Supervisor** | The sole user role — views and filters the call monitoring table. |
| **JWT** | JSON Web Token — stateless auth token returned by `/api/auth/login`, sent as `Authorization: Bearer` header. |
| **Specification** | JPA Specification — a composable predicate builder for dynamic query filtering (Spring Data JPA). |
| **Period Filter** | Date-range filter on `callTimestamp`, constrained to the latest 3 months. |
| **Sentiment Filter** | Dropdown with two options: "Below 70%" and "70% or above". |
| **Seed Data** | Initial 100 call records inserted by `CommandLineRunner` when the table is empty. |

## 5. Implementation Plan

Ordered phases with intended commits (Conventional Commits). Work is coordinated
on the single branch `feature/US-01-call-monitoring` and dispatched to the
backend, frontend, and devops sub-agents.

### Phase 0 — DevOps: Compose healthcheck (prerequisite)

**Commit:** `ci(infra): add healthcheck condition to compose.yml`

- Update `compose.yml` so the backend `depends_on` uses
  `condition: service_healthy`, ensuring it waits on a healthy Postgres.

### Phase 1 — Backend: entity, repo, seed

**Commits:**
1. `feat(db): add CallRecord entity with JPA mapping`
   - Fields: `id` (Long, PK), `callId` (UUID, unique), `callTimestamp`
     (LocalDateTime), `csName` (String), `customerName` (String),
     `sentimentScore` (Short, 0–100), `createdAt`, `updatedAt`.
   - `@PrePersist` / `@PreUpdate` maintain audit timestamps.
2. `feat(db): add User entity for authentication`
   - Fields: `id` (Long), `username` (String, unique), `password` (BCrypt),
     `createdAt`.
3. `feat(db): add JPA repositories for CallRecord and User`
   - `CallRecordRepository` extends `JpaRepository` +
     `JpaSpecificationExecutor<CallRecord>`.
   - `UserRepository` with `findByUsername(String)`.
4. `feat(db): seed 100 call records and 1 admin user via CommandLineRunner`
   - Admin `admin` / `admin123`; 100 call records (random Indonesian names,
     weighted sentiment, 6-month span) — only when tables are empty.

### Phase 2 — Backend: specification, endpoint, security

**Commits:**
5. `feat(backend): add CallRecordSpecification for dynamic filtering`
   - Builds `Specification<CallRecord>` from `q`, `startDate`/`endDate`,
     `sentiment`; maps `sort` to the correct JPA path.
6. `feat(backend): add paginated GET /api/calls endpoint`
   - Accepts all filter/sort/page params; returns `Page<CallRecord>`; JWT-protected.
7. `feat(security): add JWT auth with login endpoint`
