# Spec — THT-MON-US-001: Call Monitoring

> Generated by `/to-spec` from the grilling session (see `grilling-plan.md` in
> this folder) plus codebase context.

---

## Problem Statement

A supervisor needs to review customer call handling and spot calls that require
attention. Currently no call-monitoring data is surfaced anywhere: the backend
has no domain model, database schema, or API, and the frontend is only a
scaffold — so a supervisor has no way to view or filter customer call sentiment.

## Solution

A supervisor logs in and lands on a single Monitoring page containing one
call-monitoring table. The table lists call records sourced from PostgreSQL via
a JWT-protected backend API, and supports search across all columns, a period
filter (limited to the latest three months), a sentiment filter (below 70% vs
70% or above), column sorting, and pagination at five records per page. All
active filters combine, sorting is preserved across pages, any filter change
resets to the first page, and a clear empty state shows when no records match.

## User Stories

1. As a supervisor, I want to authenticate with my credentials, so that I can
   access the monitoring page and the protected call data behind it.
2. As an authenticated supervisor, I want to be redirected to the monitoring
   page when I open the app, so that I reach the feature immediately.
3. As an unauthenticated visitor, I want to be redirected to the login page
   when I try to open the monitoring page, so that access stays protected.
4. As a supervisor, I want the monitoring page to load a single call-monitoring
   table, so that I can see all call records in one place.
5. As a supervisor, I want each table row to show No., Call ID, Call Timestamp,
   CS Name, Customer Name, and Sentiment Score, so that I can identify each
   call at a glance.
6. As a supervisor, I want the table to show five records per page with
   Previous and Next controls, so that I can page through the full dataset.
7. As a supervisor, I want the No. column to reflect a global position across
   all pages, so that I can locate a record within the whole dataset.
8. As a supervisor, I want to enter a keyword that searches all displayed
   columns, so that I can find calls matching any piece of data.
9. As a supervisor, I want to pick a start and end period, so that I can view
   only the calls that occurred within that inclusive date range.
10. As a supervisor, I want the selectable period to be limited to the latest
    three months, so that I stay focused on recent activity.
11. As a supervisor, I want to filter to sentiment below 70%, so that I can
    surface calls that likely need attention.
12. As a supervisor, I want to filter to sentiment of 70% or above, so that I
    can view well-handled or positive calls.
13. As a supervisor, I want all active filters to apply together whenever any
    filter value changes, so that I get a combined result set.
14. As a supervisor, I want the table to reset to the first page whenever any
    filter changes, so that I always start at the top of the result set.
15. As a supervisor, I want to click a column header to sort that column
    ascending and then descending on repeat clicks, so that I can order calls
    the way I need.
16. As a supervisor, I want active filters and the current sort order to be
    preserved when I change pages, so that my view stays consistent.
17. As a supervisor, I want to see an informative empty state when no record
    matches the active criteria, so that I know the filter genuinely returned
    nothing.

## Implementation Decisions

- **Modules built/modified**
  - Backend: `User` and `CallRecord` entities; repositories for both; a
    `CallRecordSpecification` for dynamic query composition; a call-monitoring
    controller; JWT service, filter, and security configuration; an auth
    controller; a `CommandLineRunner` seed component; matching unit tests.
  - Frontend: app bootstrap (PrimeVue, Pinia, Vue Router); an auth store, an
    Axios instance with auth interceptors, and a navigation guard; a login
    view; a `useCallRecords` composable over TanStack Vue Query; a filter bar,
    a call data table, an empty state, and a monitoring view; matching Vitest
    and Playwright tests.
  - Infrastructure: compose healthcheck gating so the backend waits on a
    healthy Postgres; README updates including the seeded credentials and the
    required AI Usage section.

- **Entity schema** — `CallRecord` carries a Long primary key, a unique UUID
  `callId`, a `callTimestamp`, a `csName`, a `customerName`, a 0–100
  `sentimentScore`, plus `createdAt`/`updatedAt` audit timestamps. `User` carries
  a Long primary key, a unique `username`, and a BCrypt-encoded `password`.
  `callId` (UUID) is the user-facing identifier; the Long key is internal.

- **API contract** — A single endpoint `GET /api/calls` returns a Spring Data
  page of call records. Query parameters: `q` (cross-column ILIKE search),
  `startDate`/`endDate` (inclusive callTimestamp range), `sentiment`
  (`below70` | `above70`), `sort` (`callId` | `callTimestamp` | `csName` |
  `customerName` | `sentimentScore`), `order` (`asc` | `desc`), `page`
  (0-based), `size` (default 5). Response is `{ content, page, size,
  totalElements, totalPages }`. All filters AND together server-side.

- **Authentication** — Passwordless username/password login via
  `POST /api/auth/login` returning a signed JWT. Every `/api/**` endpoint except
  `/api/auth/**` requires a valid Bearer token. Passwords are BCrypt-hashed.
  Default seeded supervisor: `admin` / `admin123`.

- **Frontend auth flow** — A Pinia auth store holds the token and login/logout
  actions. An Axios instance attaches the token on requests and redirects to
  login on a 401. A Vue Router guard redirects unauthenticated users to `/login`
  and authenticated users to `/monitoring`.

- **UI/UX** — All UI text is English. Table columns: No., Call ID, Call
  Timestamp, CS Name, Customer Name, Sentiment Score. Sentiment renders as an
  integer percentage. The period filter is a single PrimeVue DatePicker in
  range mode clamped to the latest three months (falling back to two separate
  pickers if range mode is problematic). The sentiment filter is a dropdown
  with All / Below 70% / 70% or above.

- **Seed data** — On an empty table, seed 100 `CallRecord` rows over the last 6
  months using random Indonesian agent and customer names, with sentiment
  weighted so roughly 60% are below 70 and 40% at or above 70.

## Testing Decisions

- **What makes a good test** — Test external, observable behavior, not internal
  implementation. Backend tests assert query semantics and HTTP behavior;
  frontend tests assert rendered output and user interactions against mocked
  API responses.

- **Backend** — Unit tests for the specification (verify predicates compose
  correctly for search, date range, and sentiment), the JWT service (generation
  and validation round-trip), and the controller (paginated, filtered, sorted
  responses; authenticated vs unauthenticated access). Run via `mvn test` inside
  the Docker build.

- **Frontend unit (Vitest)** — `useCallRecords` composable (filter composition
  and refetch against a mocked API), `LoginView` (validation and successful
  login), `FilterBar` (filter change emits), and `CallDataTable` (column
  rendering and pagination). Run via `npm run test`, plus `npm run lint` and
  `npm run typecheck`.

- **E2E (Playwright)** — A single full journey: login → monitoring table loads →
  search → period filter → sentiment filter → paginate → sort. Written with the
  feature but only run once the whole feature is implemented, against the
  Dockerized stack.

## Out of Scope

- The live-coding monitoring summary story (referenced but separate).
- Real sentiment analysis / ML scoring — sentiment is pre-stored data.
- Role management or multiple user roles beyond the sole supervisor.
- Export, reporting, or analytics beyond the table.
- Writing our own schema migrations — the schema is managed by JPA
  `ddl-auto: update`; no migration tool is introduced.

## Further Notes

- All data displayed in the UI must come from PostgreSQL via the backend API —
  never hardcoded in the frontend.
- Feature work lives on branch `feature/US-01-call-monitoring` and follows the
  Conventional Commits convention; tests/lint/typecheck must pass before each
  commit.
- The seed distribution is weighted so the sentiment filter is demonstrably
  useful during review.
